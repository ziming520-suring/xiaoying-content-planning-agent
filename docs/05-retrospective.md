# 第二阶段复盘

第五阶段结论：流程、硬约束与内容事实必须分别评估。25个任务都达到预期终态，并不能掩盖P04的3次无效动作或17份脚本中8份具体事实扩写。重复测试也说明temperature=0并不保证措辞固定。下一步优先改进来源约束的内容生成与复核，再按冻结场景复测；不继续用成功保存率替代文案质量。

最关键的分离是计划预计费用与执行已发生费用。失败消耗 3 后，再执行 8 单位方案会使总额达到 11；不能因为替代方案单独低于预算 10 就放行。

验证发现并修复：测试中的 SQLite 连接未关闭导致 Windows 临时目录清理失败；非法步骤类型导致 TypeError；新版本错误复用旧保存状态导致漏估保存耗时；已完成检索节点可伪造上游依赖；极端日期加法溢出；空素材估算与生成判断不一致。

上述问题均有可复现测试。第一次工具模块尚不存在时的测试运行失败说明缺少实现，不等于业务断言已验证；后续边界回归是在已有实现上观察失败再修复。

下一步应把工具账本与成功结果放入统一持久化事务，并实现 request_id 重放、任务状态、CLI 和未知结果恢复。当前 SQLite 只保存产物，不能声称任务可在重启后续跑。

没有持续人工计时器，不报告未经核实的总工时。

## 第四阶段补充

远程请求不能依靠SQLite回滚撤销。把业务预留、API调用身份、供应商响应缓存分开持久化，才能在回执已收到而业务尚未入账时恢复且不再次付费。缺少回执时保留预留，不猜测成功或失败。

真实模型会违反工具参数定义：首轮预算场景在save_plan多传step_id并原样重试，导致未完成。保留失败Trace后补充准确字段与纠错规则，未放宽工具校验。脚本文本也可能扩写素材未说明的细节，因此“来源ID合法”和“内容有依据”必须分开核验。

## 第三阶段补充

本地业务工具与持久化状态必须共用事务，不能先保存独立产物再记录费用。本阶段通过在保存事务中让子进程退出，证明确实没有留下半提交产物；后续显式续跑保留生成结果。

进程锁与数据库状态承担不同职责：running 只是记录，不证明进程活着；文件锁必须取得后才能判断旧运行已中断。还要防止多次resume覆盖尚未驱动的pending运行。

审阅发现空数据库文件和非法Unicode都可能影响后续正常使用，因此错误处理既要给出明确响应，也要让修复后的合法请求可以继续。第四阶段不能将本地SQLite事务套用到远程模型收费调用。
