# 第二阶段方案

当前方案：CLI请求进入Runtime，任务固定Catalog快照，模型在事务外根据实际观察调用四类工具或finish；工具工作台控制计划版本、费用、时间、依赖和结果复用，SQLite原子保存本地状态。真实生成分为持久化业务预留、事务外API请求、缓存响应及本地结算三步。模型不能直接修改账本或任务硬约束。默认离线策略可免费复现，在线模式采用百炼原生工具调用，无外部Agent框架。具体边界见[Runtime契约](07-runtime-contract.md)和[在线接入](09-live-integration.md)。以下为历史阶段方案。

本文件保留第二阶段架构说明。当前第三阶段已将工具工作台状态和费用纳入持久化事务；新版职责和恢复边界见 [Runtime 契约](07-runtime-contract.md)。

Catalog 严格读取合成资料和费用表，检索使用标题/关键词的确定性双向包含匹配，不宣称语义检索。返回深拷贝防止调用者篡改可信数据。

ToolWorkbench 由可信编排代码持有。它管理本阶段内存中的计划版本、成功结果、执行尝试及费用时间。四类工具返回统一 tool_status/result/error。模型将来只能提交受限工具参数，不能访问工作台属性、注入故障或数据库函数。

估算从成功结果和表内费率重建剩余费用，包含历史失败消耗、最终估算和保存耗时；不可行计划仍作为工具成功观察返回，但 feasible=false。没有素材也不可行。新估算有新的 estimate_id，计划内容相同则版本不变。

生成工具当前为 offline_mock，仅将素材事实组织成带来源 ID 的文本。economy/premium/quick 是合成成本/时间策略，当前并不代表不同创意质量；真实生成适配器留到第四阶段。

保存前核对当前版本、依赖、有效脚本及费用时间，必要时自动进行最终估算。SQLite 使用事务和 task_id+plan_version 唯一约束保存快照；同版本不同内容拒绝，不覆盖旧产物。内部数据库写函数只供可信代码调用，并非独立对外业务校验入口。

副作用预检查拒绝不收费、不推进时间；确定失败按表收费；不确定提交保留预留并阻止新执行。异常后的持久化恢复、解除 unknown、运行者锁及进程故障测试尚未实现，不把代码中的保守状态分支当作完整恢复证明。

计划只包含最多 20 个业务步骤，最多 20 个依赖/输入引用。检索发生在规划前；可在计划中列出已完成的检索节点，但它不能依赖未来步骤。重新检索后再提交新计划。保存必须直接依赖所有生成节点，且为唯一末尾保存节点。

整个任务级状态机、request_id 重放、全局执行上限、跨进程续跑及费用持久化为第三阶段职责；本阶段各工具能独立调用和验证，不提供任务已完成状态。
