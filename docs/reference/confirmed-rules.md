## 1. 题面契约（原文）

来源：[考核题目](exam.md)“项目题 2：内容任务规划 Agent”。

- **用户与目标：**帮助运营人员在预算与截止时间内完成一份内容活动方案。
- **输入与材料：**主题、预算、截止时间；合成素材、工具费用与耗时表。提供素材检索、脚本生成、成本估算、方案保存工具。
- **交付结果：**任务计划、步骤状态、工具结果、费用合计、已保存方案或未完成原因。
- **动态决策：**模型根据成本超限、工具错误或部分成功结果，调整计划、选替代方案或停止；保留已成功步骤的结果。
- **必须验收：**正常完成；缺预算或截止时间；工具失败；预算超限；重复执行。失败步骤续跑属于加分项。

参考实例原文：预算 10 个模拟单位；初始方案估算 12，替代方案估算 8。模型观察到超预算后改选 8 的方案，再估算和保存。若没有可行方案，返回未完成及缺口；不能把失败步骤记为成功。

审核要点原文：核对预算计算、步骤依赖与实际状态；注入一次失败，观察是否调整计划且保留成功结果。高分依据是合理重规划；无状态、无失败处理只能证明完成串行调用。

通用硬要求：真实模型驱动动作循环；至少两条根据工具观察调整动作的路径；至少三组实际输入、输出和 Trace，覆盖正常、信息不足、工具失败及本题全部验收点；执行上限；离线 Mock 明确标记；完整代码、测试、五份文档、运行说明和交卷信息。以上最终逐项引用运行证据，不能以设计预期代替实际结果。

## 4. 预算口径（建议 D01）

预算是任务整个执行过程允许消耗的模拟工具费用上限，包含已经发生的失败尝试费用。模拟单位使用非负整数，拒绝小数和布尔值；0 是合法预算，是否可完成由工具表决定。

- 工具表为每个操作模式提供成功费用/耗时和确定失败费用/耗时；在执行前可计算本次最大可能消耗。
- 参数无效、依赖不足、预算或时间预检查拒绝：没有开始业务执行，不扣费、不推进模拟时间，但计入动作次数。
- 已实际执行的确定成功或确定失败：按对应工具表记录费用和耗时；同一 attempt_id 只结算一次。
- 工具执行前预留本次最大费用；成功或确定失败后按实际值结算并释放差额。执行结果无法确定时保留预留，先核对原尝试，不能直接新建尝试。
- 新尝试前检查“已结算费用 + 未决预留 + 本次最大费用 <= 总预算”。
- 估算输出分别给出 spent_cost、reserved_cost、remaining_cost_estimate、projected_total_cost。预计总额包含历史失败和被放弃方案已发生的消耗，不退还沉没成本。
- 修改方案不会清零费用；重试是新 attempt，可能新增费用；重放同一请求不是重试，不新增费用。
- 为便于还原题面 12→8 示例，建议合成表的检索、估算、保存费用为 0，生成按方案模式收费；耗时另列。此为测试设计，不是现实服务价格。
- 模拟业务费用与真实模型 API 费用使用独立账本，不能相互抵扣。

## 5. 时间口径（建议 D02）

- 请求带明确时区的 start_time、deadline；内部归一化为 UTC。缺少 start_time 时由 CLI 显式提供固定演示时间，不暗取系统时间。
- 使用任务级逻辑时间，不等待真实耗时，不继承项目 1 的全局时间推进接口。
- 工具表耗时为非负整数秒，成功和确定失败均按表推进；重复请求不推进。
- 顺序执行，预计结束时间 = 当前逻辑时间 + 剩余依赖步骤预计耗时，必须包含保存步骤。
- 执行前按本次最大可能耗时校验，未决尝试占用相应时间预留；未核实前暂停该任务的后续执行。
- 恰好在 deadline 完成允许；初始 deadline 必须严格晚于 start_time。时间已耗尽时不启动新的业务执行，只允许查询、恢复核对和停止。
- 超时不能擅自改截止时间；可选较短方案或返回未完成。
- 该口径证明模拟费用与时间约束正确，不证明真实 API 延迟满足墙上时钟截止时间；真实模型耗时单独记录。

## 6. 任务和步骤（建议 D03）

任务生命周期：waiting_input → ready → running → completed / partial / incomplete。waiting_input 补齐后可进入 ready；partial/incomplete 显式续跑后回到 running；completed 重复执行返回已保存成果。

| 任务状态 | 含义 |
|---|---|
| waiting_input | 缺主题、预算或截止时间；列出缺口，不执行收费工具 |
| ready | 输入完整、尚未开始 |
| running | 正在执行 |
| completed | 满足硬要求的当前方案已经成功保存 |
| partial | 当前未完成，但存在仍适用的成功业务结果 |
| incomplete | 当前未完成，且无适用的成功业务结果 |

partial/incomplete 必须附 stop_reason，例如 budget_exceeded、deadline_exceeded、tool_failed、no_material、no_feasible_plan、step_limit、pending_reconciliation。一次估算成功不单独算可交付业务成果；检索到可用素材、成功生成脚本属于可保留成果。

步骤状态：pending、running、succeeded、failed、blocked、unknown。依赖未满足为 blocked；结果不能核实为 unknown；计划放弃通过步骤所属计划版本的 superseded 标记表示，不改写实际成功/失败历史。

任务完成与单个工具成功不同。模型的 finish 只是停止请求，最终状态由程序读取可信记录重建。

## 7. 计划、依赖和生成（建议 D04）

- 正常链路：检索素材 → 制定计划 → 估算 → 生成脚本 → 最终估算/约束核验 → 保存。
- 制定计划和更改计划由模型选择，经程序校验后登记版本；不需要额外暴露任意数据库写工具。
- 生成必须引用检索实际返回的素材 ID、版本和片段；模型选择的制作模式必须存在于工具表。
- 脚本生成工具在线模式调用模型生成文本，离线模式明确标记模板/Mock。真实生成调用也受独立 API 预算限制；第一阶段不选供应商。
- 保存方案最少包含活动主题与目标、选定制作方式、素材来源、脚本、执行步骤及依赖、费用与耗时、当前计划版本。内容数量按合成方案配置，避免把“活动方案”扩展成完整营销平台。
- 保存时从记录重建检查：当前版本、依赖、有效脚本、实际费用及剩余预留、时间、来源引用；不接受模型自报的通过标记。
- 素材文字是数据，不能授权工具或改变预算规则。来源引用可以校验；内容语义质量另外评估，不声称程序完全识别所有无依据描述。
- 模型可以补查、选择替代模式、重试或停止；不能修改用户硬要求或伪造成功。
- 每次新计划仍受相同主题、预算、截止限制；修改硬要求须由用户显式创建新任务，第一版不做已执行任务的约束变更。

## 8. 重复执行和恢复（建议 D05）

- 写请求用 operation + request_id 标识，并绑定规范化参数。相同键同参数返回原已记录响应，相同键不同参数冲突。
- task_id 为业务唯一标识：换 request_id 也不重复创建同一任务；不同参数冲突。
- 校验拒绝不占执行尝试；实际执行后的确定失败记录同样持久化，原键查询返回该失败。再次真正执行必须有新的 attempt_id，并保留旧失败。
- 这与项目 1 只重放成功结果的口径不同：第二题失败也可能已经消耗费用，不能用原键悄悄重新执行。
- 重复 run 不重做已完成成果；未完成任务要求显式 resume。一次只允许一个运行者推进同一任务；不在 SQLite 写事务内等待模型/外部服务。
- 复用键至少包括操作、输入、制作模式、素材版本、工具表版本和上游结果身份。只复用成功且仍适用的结果；unknown 先核对，failed 不伪装为成功。
- 同任务保存同版本方案只生成一份结果。保存失败保留此前脚本、素材与费用记录。数据库提交结果不确定时，原键核对，不宣称成功。
- 崩溃恢复：单机运行者持有进程级排他锁（进程退出由系统释放），仅数据库 running 标记不能证明仍有活跃执行。恢复入口取得锁后核对旧运行和未决尝试；核实已提交的结果则恢复记录，已开始但不能核实的尝试转 unknown 并保留预留，任务以 partial/incomplete 和 pending_reconciliation 停止。全部未决项解决后才能新建续跑 run；原启动请求始终返回原 run_id，不隐式重启。具体 Windows 锁实现到状态层阶段验证。

## 9. 执行上限、证据与范围

建议每次 run/resume 最多 24 个模型动作，finish 与非法动作均计入；续跑保留累计记录，单次上限不等于无限免费重试。无并行工具调用。固定模型 API 费用总限额后，所有真实调用共享该限额。

Trace 记录步骤、计划版本、attempt_id、工具参数、结果摘要、简要决策依据、费用/时间变化及最终状态；不要求内部思维过程。Mock、故障注入、模拟时间和真实模型动作明确区分。

后续开发顺序与已讨论的六阶段一致：规则 → 资料和工具 → 本地状态闭环 → 真实决策 → 续跑与验证 → 交付。不先开发通用 Runtime、前端、分布式恢复或外部付费执行系统。
